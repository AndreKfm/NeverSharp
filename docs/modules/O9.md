# O9: per-file overhead, up to 3 variants — brief

Step O9 of Track O ([track-o-steps.md](../track-o-steps.md)), added after the Track O endpoint (G = 0.60 [0.59, 0.61] against typescript-go; that result stays as it is, later gains are reported as additional runs next to it, pre-registration §8 "One final measurement"). Goal: close part of the gap to tsrs (secondary reference, 1.52 [1.50, 1.54]). The probes in `results/track-o/probes/io/NOTE.md` show that the gap is user CPU in parsing (vscode single-threaded: Track O 3.87 s, tsrs 1.36 s), not I/O or scheduling. This step removes fixed costs per file that the CPU profile shows. Pre-registration §5.4: at most 3 variants; variant A is `main` (no attempt). Written by the orchestrator before any attempt started. The standing rules of [README.md](README.md) apply (Track O follows pre-registration §5.4).

## The variants

Both attempts do the common part identically, then differ in how the per-file result owns its node data:

- **Common:** the parser pool as a per-thread cache (`[ThreadStatic]` instance with the `ConcurrentBag` or a lock-free fallback only when a thread already holds one; counterpart: typescript-go's `sync.Pool` in `getParser`/`putParser`, which caches per processor); the interning hash table reused per thread without per-file allocation or full zeroing (e.g. generation stamps, or clearing only the used slots); any other per-file setup cost you find in the profile.

| Variant | Result's node data | Ideas to evaluate (not prescribed) |
|---|---|---|
| **A: main** | exact-size pinned copies made by `Seal` | — (measured as the reference) |
| **B: hand over the scratch** | the result keeps the arrays it was built in; the thread's scratch is replaced lazily for the next parse | trim only when the over-capacity is large (e.g. > 2× and above a size threshold), otherwise no copy; size the next scratch from recent files; watch peak memory and bytes allocated |
| **C: per-thread slabs** | records, list headers and list elements are written into large per-thread slabs (managed pinned or native memory, as O1 does for text); a result references its range of a slab and keeps the slab alive (reference count or ownership by the last result) | no copy and no per-file array allocation; release with the result (`SourceFile.Release()`, finalizer as backstop) if native |

All variants keep: the `NodeStore` / `NodeList` / `TextTable` API used by parser and factory, results valid after the parse and independent of later parses, thread safety, Gate 1, and the tool contract (`SourceText.Read`, `Parser.ParseFile`, `Parser.CreateSourceFile(fileName, string, …)`, `SourceFile.TextLength`, `NodeCount`, `ParseDiagnostics`, `JsDocDiagnostics`, `SourceFile.Release()`).
