# O1: file reading and decoding, up to 3 variants — brief

Step O1 of Track O ([track-o-steps.md](../track-o-steps.md)): how a file gets from disk to the characters the scanner reads. The seam (commit `49dcb44`) moved reading into Track O: `IO/SourceText.cs` (`SourceText.Read(path)`, sys.ts semantics), `Parser.ParseFile(path, fileName, …)`, the parse-only driver's Track O build calls `ParseFile`, and `tools/NeverSharp.ReaderCheck` (a gate step of `--track optimized`) compares `SourceText.Read(path).Chars` with the reference decode on every corpus file. Pre-registration §5.4: at most 3 variants per step; variant A is the seam as committed (no attempt). Written by the orchestrator before any attempt started. The standing rules of [README.md](README.md) apply (Track O follows pre-registration §5.4).

## Starting point

Track O after O-NA plus the seam (`main`): tuning corpus `cs-o-aot-ws` 473 ms. The O5a/O-NA allocation profiles attribute about 39 MB on the tuning corpus to file contents as bytes (`File.ReadAllBytes`), plus the decoded `string` per file (about twice the UTF-8 size again). The source text is a `string` throughout Track O: `TextTable.Source` (`Arena/Text.cs`), the scanner (`Scanner/Scanner.cs`: `text[pos]`, comment-directive and JSDoc helpers, `ComputeLineStarts`), `NodeStore.SourceFileText`, `SourceFileNodeLike.Text` (`ISourceFileLike`).

## The variants

| Variant | Reading and where the text lives | Ideas to evaluate (not prescribed) |
|---|---|---|
| **A: baseline (the seam)** | `File.ReadAllBytes` + `Encoding.*.GetString`: one `byte[]` and one `string` per file | — (measured as the reference) |
| **B: pooled bytes, char arena** | Read into a pooled (per-thread or `ArrayPool`) byte buffer with `RandomAccess.Read`/`FileStream` of known length; decode with SIMD `System.Text.Unicode.Utf8.ToUtf16` (UTF-16 BOMs: copy/byte-swap) into a char buffer owned by the parse result (exact-size pinned or pooled-and-sealed array, as the node store does) | no `byte[]` and no `string` per file on the hot path; scanner and text table on `ReadOnlySpan<char>` / `ReadOnlyMemory<char>` or a `char[]` + length; ASCII fast path |
| **C: memory-mapped, native text** | `MemoryMappedFile` (or `RandomAccess` into native memory) and SIMD decode into `NativeMemory.Alloc`ed UTF-16; the text's lifetime is tied to the parse result (released by the result, `SafeHandle` or finalizer as a backstop) | scanner on `char*` / span over native memory; no managed text at all for the source; costs of mapping small files vs reading them |

B and C replace `string` as the type of the source text inside Track O by a text handle of their own design (span-based). Both must keep:

- the tool contract: `SourceText.Read(path)` returning the file's text, `.Chars` (`ReadOnlySpan<char>`), `.Length`; `Parser.ParseFile(path, fileName, options, setParentNodes, scriptKind)`; `Parser.CreateSourceFile(fileName, string text, …)` for the dump tool and the tests (it may wrap the string); `SourceFile.TextLength`, `NodeCount`, `ParseDiagnostics`, `JsDocDiagnostics`;
- results valid after the parse and independent of later parses (a pooled buffer must not be reused while a result refers to it); thread safety (parallel driver, one work item per file);
- Gate 1 byte-identical; sys.ts decode semantics exactly (BOMs, invalid UTF-8 replaced by U+FFFD as `Encoding.UTF8` does, odd trailing byte of UTF-16 dropped) — the reader check proves it.

A `string` of the source may still be produced lazily on cold paths that need one (e.g. `ISourceFileLike.Text` for diagnostics, the dump tool), never on the parse's hot path; such allocations are `[NoAllocUnchecked(reason)]` or outside annotated code and listed.
