Module C10 of Phase 3 ([phase3-plan.md](../phase3-plan.md); draft amendment [preregistration.md](../preregistration.md) §17). Track O only. Written by the orchestrator. Standing rules of [README.md](README.md); run only the tests and gates your change affects. ## Starting point

`main` after Gate C (0a9217f): Gate C counts as passed (50,176 of 50,177 units identical; 027977 times out under the gate's load only, accepted by the author). Gate C checks one-file programs. The benchmark programs are whole repositories: each repository's file list (`artifacts/bench/filelists/<repo>.txt`, `.ts .tsx .mts .cts`) as one program. Drivers and harness: `tools/NeverSharp.ParseDriver` (`--bind`, driver contract in docs/benchmark-harness.md §4.1), `harness/bench/bench.mjs` (configurations, profiles §16), `harness/bench/go/parse.go` with `build-go.mjs` (typescript-go 7.0.2, pinned in `external/typescript-go`), `harness/bench/rust/parse-rs` (tsrs). The C# program layer is `src/NeverSharp.Optimized/Program/`; the checker dump `tools/NeverSharp.Dump.Optimized` builds programs with it.

**The gap this module closes first:** tsc 6.0.3 with `noResolve: true` still resolves module names; it only does not add the resolved files to the program. An import of a file that is in the program resolves and is checked across files; an import of a file outside the program reports 2307. (Checked by the orchestrator: `a.ts` importing `./b` with `a.ts`, `b.ts` as roots gives the cross-file 2322; `./c` outside the program gives 2307; effective module resolution `Bundler`, module `ES2022`.) The C# program layer has no module resolution: `ResolveExternalModule` finds ambient modules only, so every relative import of a repository program would report 2307 and the checker would do far less work than tsc and tsgo.

## Goal

1. **Module resolution in the program layer.** Port what program.ts and moduleNameResolver.ts do for the Gate C options (TypeScript 6.0.3's defaults with `noResolve: true`; effective resolution Bundler): resolve every module name of every file once when the program is built (the resolution is recorded per file and import, as `resolvedModules`), with the host's file system checks as tsc makes them (extensions in tsc's order, directory `index` files, `package.json` `types`/`exports` where a repository needs them; `node_modules` of the repositories are not installed). Then port the tail of checker.ts `resolveExternalModule` that uses it (`getResolvedModule`, `getSourceFile` of the resolved file name, the resolution diagnostics and the errors for files resolved but not in the program). Gate C must stay as it is: one-file units resolve nothing new, so the dumps must not change (sample after the change, full corpus at the end).
2. **C# check mode in the parse driver** (`--check`, same contract as `--bind`): parse and bind every file as `--bind` does, build one `Program` with the default library and the Gate C options, then check every file: semantic diagnostics of every file and the global diagnostics, as tsc's `getSemanticDiagnostics` / `getGlobalDiagnostics` (no suggestion diagnostics: typescript-go's command line does not compute them either). Parallel: the same number of checkers as typescript-go's default checker pool (4, `internal/compiler/checkerpool.go`, capped by the file count) and the same assignment of files to checkers; each checker on its own thread. `--single`: one checker, parse/bind/check sequential. The JSON line additionally reports the diagnostic count (total and per category) as proof of work. An option `--dump-diagnostics <file>` writes the canonical diagnostics (file, start, length, code, category, flattened message) for the equivalence check of 5.; never used in timed runs.
3. **typescript-go 7.0.2 check mode** in `harness/bench/go/parse.go` (`--check`): create the program from the same file list with its own compiler host on the real file system and the same options given **explicitly** (typescript-go's defaults are TypeScript 7's; write the option table the C# side uses as its defaults and pass every entry that differs), then the semantic and global diagnostics of every file through its default checker pool; `--single` single-threaded. Report the same counts. Build reproducible as `build-go.mjs` does; typescript-go's own build settings stay.
4. **tsrs:** check whether tsrs 0.18.0 exposes a checker that can be called on a program; if not, document why not (it is then not reported, as §17 says).
5. **Equivalence check of the repository programs (not timed, not a gate yet):** a script (e.g. `harness/bench/check-equivalence.mjs`) that runs tsc 6.0.3 (`harness/astdump/node_modules/typescript`) on each repository's program with the same options and compares its diagnostics with the C# driver's `--dump-diagnostics` output. Report per repository: diagnostic counts per side, identical or not, differences grouped by code with one example each. Fix the differences whose cause is the program layer (resolution, file set, options, global diagnostics); list checker differences with a small reproduction where it is cheap to make — they are not fixed in C10. Also report typescript-go's counts next to them (expected to differ: TypeScript 7).
6. **Configurations and profile** in `bench.mjs`: `cs-o-aot-ws-check`, `cs-o-aot-srv-check` and their `-single` variants, `tsgo7-check`, `tsgo7-check-single`; a profile `check` with these (variance gate binding rows: `tsgo7-check-single`, `cs-o-aot-ws-check-single`, as §17 drafts); validation as for bind (file counts, driver names, a diagnostic count reported).
7. **Functional check (not a measurement):** every new configuration once on the five benchmark repositories and the tuning corpus: files, diagnostic counts, peak memory if the harness reports it, and the wall time of that one run (the orchestrator needs it to plan the protocol run: `--runs` × configurations × repositories). If a C# run crashes, times out or takes unreasonably long (say > 10 minutes for one repository), report it with the repository instead of optimizing; optimization comes after the measurement, profile first.
