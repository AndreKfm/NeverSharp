# M5: JSDoc parser (Track F) — brief for porting attempts

Module M5 of [phase1-plan.md](../phase1-plan.md) §4: the last Track F module; its gate is Gate 1 proper. Every attempt receives exactly this brief (pre-registration §5.2; from M5 on two attempts, Opus 5.5 and Sonnet 5.5, at medium effort: prereg/v3). Written by the orchestrator before any attempt started. The standing rules of [README.md](README.md) apply.

## Scope

The 4 units (1,088 lines) of `namespace JSDocParser` in `parser.ts` listed in [M5-units.md](M5-units.md): `parseJSDocTypeExpression`, `parseJSDocNameReference`, `parseJSDocComment` and `parseJSDocCommentWorker` (1,039 lines with its inner functions: tags, type expressions, `@param`/`@property`/`@typedef`/`@callback`/`@template`/`@see`/`@link`, comment text, both `ParseAll` and `ParseForTypeErrors`/`ParseForTypeInfo` behaviour through the scanner's JSDoc mode). The v6.0.3 `scanJsDocToken` defect is in the merged scanner as it is (pre-registration §5.3); a unit that loops forever times out in the dump, as in tsc.

Not in scope: `parseIsolatedJSDocComment`, `parseJSDocTypeExpressionForTests` (test and language-service entry points).

The merged modules are the base: M1 (`Core/`), M2 (`Scanner/`), M3 + M4 (`Factory/`, `Parser/`: the parser, its state, the factory). The parser currently calls a stub, `Parser.JSDocParserParseJSDocComment` in `Parser/Parser.JSDocStubs.cs`, which throws `NotImplementedException("M5")`; with `JSDocParsingMode.ParseNone` it is never reached.

## API

No new API for the tools: `Parser.CreateSourceFile` with `JsDocParsingMode = ParseAll` (or `ParseForTypeErrors`) now parses JSDoc; `node.jsDoc` is set through `JSDocContainers.SetJsDoc`; `SourceFile.JsDocDiagnostics` holds the JSDoc diagnostics as TypeScript does. Thread safety as in M3 + M4 (no mutable static state besides the parser pool).
