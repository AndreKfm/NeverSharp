### O6a: handle-based node API

Brief: [modules/O6a.md](modules/O6a.md). One attempt (Opus 5.5, high effort, no sub-agents; mechanical conversion with a one-off Roslyn rewriter in its scratch folder), about 31 of 100 gate runs. Commit 6ba80cf (branch `attempts/O6a`), merged.

- **Design:** nodes are `readonly struct Node` (one `int`); `NodeStore` per parse holds one 40-byte record per node (kind, flags, pos, end, parent, slot offsets, transform flags, modifier-flags cache, original) plus per-kind blocks of int slots (child handles, scalars) and object slots (strings, node lists); 160 generated field accessors, `Is{Class}` tests and `ForEachChild` over handles (`tools/NeverSharp.Generate/emit-optimized.mjs`). `lookAhead`/failed `tryParse` truncate the store to a mark. Lists stay `List<Node>` (O7), texts stay strings (O5).
- **Gate (orchestrator rerun):** Track O passes every gate (50,177/50,177 in G1a, G1 ParseNone, Gate 1); Track F still passes. The tool diff is only the Track O traversal in `AstDump.DumpUnit` (reviewed line by line); the driver and benchmarks needed no change.
- **Measurement (development, not a protocol result):** `M5.ParseTuningCorpus` (ParseForTypeErrors, NativeAOT, BenchmarkDotNet): Track F 2,495 ms [2,485, 2,535], 737.8 MB, GCs 85/71/4; Track O after O6a 1,649 ms [1,635, 1,659], 823.5 MB, GCs 66/34/3. About 34 % faster with half the gen1 collections, although it allocates 12 % more (store over-capacity and growth garbage, delegates for method groups that gained a store parameter): the bytes now die young. Raw reports: `results/track-o/O6a/`.
- **Harness fix found on the way:** BenchmarkDotNet's NativeAOT build does not pass `-p:NeverSharpTrack` on; a first Track O measurement had silently measured Track F (identical allocation exposed it). The track is now set as an environment variable (documented in the benchmark project).
- Open for O6b (from the attempt): shrink the 40-byte record (rare fields to side tables), the mostly-null `JsDoc` object slot of 69 container kinds, initial sizing and growth (about 1.9× over-capacity), offset lookup per access, pooling the store.

### O7a: node lists as handles

Brief: [modules/O7a.md](modules/O7a.md). One attempt (Opus 5.5, high effort, no sub-agents; call sites converted with rewrite scripts), about 22 of 100 gate runs; commit f48ed75 (branch `attempts/O7a`), merged. Both gates pass on the orchestrator's rerun (Track O 50,177/50,177 everywhere; Track F unchanged); no tool diff.

- **Design:** `readonly struct NodeList` (header index; 0 = undefined); 24-byte headers (start, count, pos, end, transform flags, trailing-comma and missing-list bits); all finished lists' elements in one `Node[]`; lists under construction as frames of a reusable scratch stack (`ListBuilder`), copied at `createNodeArray`; the store's mark covers lists, elements, frames and scratch; arrays rented from the shared pool during the parse and moved to exact-size pinned arrays at the end. The one interleaved case (JSDoc comment parts and tags) finishes its tags list first; creating a list creates no node, so node order is unchanged.
- **Measurement (development, both runs rig-compliant, idle 5.8 % / 6.2 %):** tuning corpus, cs-o-aot-ws, 20 runs: **O7a 845 ms** vs main (O6b A) 1,100 ms, ratio 0.768 [0.760, 0.774]; allocated 679 vs 693 MB; GC pause 576 vs 695 ms; gen1 collections 23 vs 30; peak working set 415 vs 448 MiB. `M5.ParseTuningCorpus` after the merge: 1.206 s, 417.0 MB (before: 1.456 s, 457.6 MB).
