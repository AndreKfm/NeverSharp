# Benchmark harness (Phase 0, task 2)

Status: built 2026-10-14; first protocol baseline 2026-10-21 (section 9). Items marked **[DECISION]** are open to veto before the pre-registration tag.
Code: [harness/bench/](../harness/bench/).

## 1. What it measures

Phase 1 compares parsers, so the benchmark is **parse-only**: read every source file of a repository and parse it, the way a compiler's program loader does, and keep all syntax trees alive until the end. Full type-checking builds (`tsc -p` against `tsgo -p`, Microsoft's published comparison) are not part of Phase 1; see section 9.

Configurations (all reported; none is dropped after the fact):

| Id | What runs |
|---|---|
| `tsc6-parse` | tsc 6.0.3 compiler API on Node 24.21.0, single-threaded (as tsc is) |
| `tsgo7-parse` | typescript-go 7.0.2 parser, parallel: typescript-go's default |
| `tsgo7-parse-single` | typescript-go 7.0.2 parser, single-threaded: what tsgo's `--singleThreaded` switches |
| `cs-<runtime>`, `cs-<runtime>-single` | Track F, `<runtime>` = `aot-ws` (primary), `aot-srv`, `jit-ws`, `jit-srv` (pre-registration §6.4); drivers built by `harness/bench/build-cs.mjs` |
| `cs-o-<runtime>`, `cs-o-<runtime>-single` | Track O, same runtimes |

The validation run rejects a driver that reports another runtime than its configuration names (e.g. a `-srv` build running with Workstation GC) or zero nodes on a non-empty list (a driver without a parser).

## 2. Pipeline

```
node scripts/fetch-references.mjs          # TypeScript, typescript-go, five benchmark repos at pinned commits
node scripts/install-tools.mjs             # Go (Microsoft build), Node, hyperfine into .tools/, SHA-256 verified
cd harness/bench && npm ci                 # typescript@6.0.3 and typescript@7.0.2 (npm aliases), lockfile-pinned
node filelists.mjs                         # parse sets per repo + manifest (counts, bytes, content hash), empty list for fixed cost
node tuning.mjs                            # tuning corpus (after harness/astdump/corpus.mjs): tests/cases units + TypeScript src
node build-go.mjs                          # Go parse driver, built like Microsoft's tsgo release binary
dotnet build peakmem -c Release -o ../../artifacts/bin/peakmem
node bench.mjs [--corpus benchmark|tuning] [--repos …] [--configs …] [--runs 20] [--warmup 3] [--mem-runs 5] [--label …]
node report.mjs artifacts/bench/results/<runId>/run.json
```

`bench.mjs` must be started with the pinned Node (`.tools/node-24.21.0/node.exe`), so the harness itself does not run behind the Volta shim.

For each (repository, configuration) pair, `bench.mjs` does three things, in this order:

1. **Validation run.** The driver prints a JSON line with the number of files it parsed; it must equal the file count of the parse set.
2. **Wall-clock** with hyperfine: `--shell=none`, warmup runs, then N timed runs, JSON export.
3. **Memory pass**, separate from timing: the driver runs under `peakmem` M times; the median peak working set and peak commit are reported.

After all repositories, every configuration is measured the same way on an empty file list (**fixed cost**: process start-up, runtime initialization, driver overhead; pre-registration A2). It is reported in its own table, with its share of the smallest repository's median, and never subtracted.

## 3. Parse set

**[DECISION B1] The parse set of a repository is every git-tracked file with extension `.ts .tsx .mts .cts` (including `.d.ts`) at the pinned commit.** No file is added or removed by hand. It is generated by `filelists.mjs`, which also records the file count, total bytes and a SHA-256 over all paths and contents; every run.json carries these values.

| Repository | Files | MiB |
|---|---:|---:|
| vscode | 11,724 | 134.6 |
| sentry | 8,932 | 43.8 |
| bluesky | 1,688 | 6.9 |
| playwright | 1,415 | 16.4 |
| tldraw | 2,508 | 13.0 |

This is a superset of what `tsc -p` compiles in these repositories: it includes tests, fixtures and tooling. For example, VS Code's set contains an 8.1 MiB copy of TypeScript's `checker.ts` used as a colorizer fixture. The alternative, the file list of each project's tsconfig (`--listFilesOnly`), requires installing every repository's dependencies and choosing a tsconfig per repository; both are choices a reviewer could attack. The git rule has no free parameter. The same set is part of the equivalence corpus ([ast-dump-format.md](ast-dump-format.md)), so every file that is timed is also checked for equivalence.

## 4. Parse-only drivers

Both drivers read a file list, read and parse each file, keep every syntax tree referenced until the end, and print one JSON line (files, characters/bytes, node count).

| | tsc 6.0.3 (`parse-ts.mjs`) | typescript-go 7.0.2 (`go/parse.go`) |
|---|---|---|
| Read | `ts.sys.readFile` | `osvfs.FS().ReadFile` |
| Parse | `ts.createSourceFile(file, text, { languageVersion: Latest, jsDocParsingMode: ParseForTypeErrors }, setParentNodes=false, scriptKind)` | `parser.ParseSourceFile(opts, text, core.GetScriptKindFromFileName(file))` |
| JSDoc | `ParseForTypeErrors`: what `executeCommandLine.ts` sets for tsc (JSDoc in JS files; in TS files only comments with `@see`/`@link`) | lazy in TS files except `@see`/`@link`: the same effective scope |
| Scheduling | sequential | `core.NewWorkGroup(single)`: typescript-go's own work group, one work item per file (read + parse), as `compilerHost.GetSourceFile` in `internal/compiler/host.go` does |
| Build | npm `typescript@6.0.3`, integrity-checked | Microsoft Go 1.26.4-1, `-trimpath -ldflags="-s -w" -tags=noembed`, `CGO_ENABLED=0`, `GOAMD64=v1`: identical to the release binary's `go version -m` except `vcs.modified` |

Decisions:

- **[DECISION B2] Trees stay alive until the end.** A program holds every source file. Discarding each tree after parsing made peak memory and GC work unrealistically small; in a first smoke test, single-threaded Go peaked at 18 MiB instead of 143 MiB on bluesky. A C# port would profit from the same artifact.
- **[DECISION B3] The tsc driver uses `ParseForTypeErrors`**, the mode tsc itself uses, and typescript-go's effective scope. The equivalence dump uses `ParseAll`, because there more coverage is better. The C# port is measured in the same mode as tsc.
- **[DECISION B4] typescript-go is measured parallel and single-threaded; the parallel default is the baseline** in relative comparisons, because that is typescript-go's wall-clock. Parallel parsing has a counterpart in typescript-go (`core.WorkGroup` in `internal/compiler/program.go`), so under the port rules the C# port may parallelize parsing the same way.
- **[DECISION B5] The Go driver is ours, the parser and scheduling are Microsoft's.** There is no parse-only mode in the tsgo CLI. The driver is a loop of about 30 lines around `core.WorkGroup`, `osvfs` and `parser.ParseSourceFile`, compiled with Microsoft's toolset and flags. This is the one place where the Go side contains code we wrote; it is kept minimal and is published.

### 4.1 Driver contract

Every parse-only driver, existing or future (tsc 6.0.3, typescript-go 7.0.2, every C# configuration of both tracks), follows the same contract, so the runner treats them alike:

| | |
|---|---|
| Invocation | `<driver> [--single] <file list>`; the file list has one absolute path per line. `--single` selects single-threaded scheduling where the driver has a parallel mode. |
| Environment | `NEVERSHARP_PRIORITY=high`: raise the own process to the high priority class as the first action (B9). |
| Work | read every file with `ts.sys.readFile` semantics (pre-registration A8), parse it in the measured mode (`ParseForTypeErrors`), keep every tree alive until the end (B2); parallel mode: one work item per file (read + parse), runtime default degree of parallelism. |
| Output | exactly one JSON line on stdout as the last line: `driver` (string), `files` (count parsed), `nodes` (sum of the parser's node counts), `priority` (`"high"` or `"normal"`, the class in effect), and the size read (`chars` or `bytes`). |
| C# drivers additionally | `allocatedBytes` (`GC.GetTotalAllocatedBytes(true)`), `gen0`, `gen1`, `gen2` (`GC.CollectionCount`), `gcPauseMs` (`GC.GetTotalPauseDuration()`), all read after the last file is parsed; the runner stores them as `runtime` in run.json and reports them in the runtime-metrics table. |
| Exit code | 0 on success; anything else fails the run. |
| Parse+bind mode (Phase 2, pre-registration §15) | `<driver> --bind [--single] <file list>`: the same work item binds each file right after parsing it, with default options, and the binder output stays alive with its tree. C# Track O: `Binder.BindSourceFile(sourceFile, new CompilerOptions())` (binder.ts `bindSourceFile(file, {})`, as the Gate B oracle binds); typescript-go 7.0.2: `binder.BindSourceFile(sourceFile)` (takes no options in 7.0.2); tsrs 0.18.0: `tsrs_binder::bind_source_file(file)`. Track F and tsc have no bind mode. The driver name carries `-bind` before the mode (`cs-optimized-aot-ws-bind-parallel`, `tsgo-7.0.2-bind-single`, `tsrs-0.18.0-bind-parallel`) and the JSON line adds `symbols` (sum of the files' symbol counts). |
| Check mode (Phase 3, draft pre-registration §17, module C10) | `<driver> --check [--single] <file list>`: the file list as **one program**, parse+bind+check. C# Track O (`cs-o-aot-ws`, `cs-o-aot-srv`): one work item per file parses it (`Parser.ParseFile`, languageVersion = the program's emit target, ParseForTypeErrors); `Program.Create(files, { noResolve: true }, DiskCompilerHost)` (TypeScript 6.0.3's default library from `lib/` next to the executable, copied from `harness/astdump/node_modules/typescript/lib` at build time; module names resolved between the program's files, `Program.Resolution.cs`/`ModuleNameResolver.cs`); then `CheckerPool` (port of typescript-go's `internal/compiler/checkerpool.go`): `Program.BindSourceFiles` (one work item per unbound file), 4 checkers (capped by the program's file count, 1 with `--single`), program file *i* (default library files first, in program order) assigned to checker *i* mod 4, each checker on its own thread visiting its files in program order: `Program.GetSemanticDiagnostics(file, checker)` for every program file, then every checker's `GetGlobalDiagnostics()` (sorted, deduplicated). typescript-go 7.0.2 (`tsgo7-check`): `compiler.NewProgram({Config: tsoptions.NewParsedCommandLine(options, files, …), Host: compiler.NewCachedFSCompilerHost(cwd, osvfs.FS(), bundled.LibPath(), nil, nil), SingleThreaded})` with typescript-go's own lib files next to the executable (`build-go.mjs` copies `internal/bundled/libs`), then `program.GetSemanticDiagnostics(ctx, nil)` and `program.GetGlobalDiagnostics(ctx)` on its default checker pool (same counts and assignment). No suggestion diagnostics, no syntactic or option diagnostics on either side. tsrs 0.18.0 has a program checker (`tsrs_compiler::new_program`, `Program::get_semantic_diagnostics`) but no check configuration (§17's profile has none; its pool may move files between checkers). The driver name carries `-check` (`cs-optimized-aot-ws-check-parallel`, `tsgo-7.0.2-check-single`) and the JSON line adds `programFiles` (with the library), `diagnostics` (total) and `errors`, `warnings`, `suggestions`, `messages`; C# also `checkers`. C# only: `--dump-diagnostics <file>` writes the canonical diagnostics for `check-equivalence.mjs` (never in timed runs). |

Options of the checked program: TypeScript 6.0.3's defaults with `noResolve: true` (`{ noResolve: true }` on the C# side and for tsc in `check-equivalence.mjs`). The Go driver passes every entry of the computed values explicitly (`checkOptions` in `go/parse.go`), so that no TypeScript 7 default applies:

| Option | TypeScript 6.0.3 computed value (C#, tsc) | Passed to typescript-go |
|---|---|---|
| noResolve | true | `NoResolve: TSTrue` |
| target | ES2025 (LatestStandard) | `Target: ES2025` |
| module | ES2022 (from target) | `Module: ES2022` |
| moduleResolution | bundler (from module) | `ModuleResolution: Bundler` |
| moduleDetection | auto | `ModuleDetection: Auto` |
| strict (and the strict family) | true | `Strict: TSTrue` |
| allowJs | false | `AllowJs: TSFalse` |
| resolveJsonModule | true (bundler) | `ResolveJsonModule: TSTrue` |
| resolvePackageJsonExports / Imports | true (bundler) | `TSTrue` / `TSTrue` |
| useDefineForClassFields | true (target ≥ ES2022) | `UseDefineForClassFields: TSTrue` |
| noUncheckedSideEffectImports | true | `NoUncheckedSideEffectImports: TSTrue` |
| esModuleInterop, allowSyntheticDefaultImports, alwaysStrict | true | not passed: always on in TypeScript 7 (deprecated as options) |
| types, lib, jsx, noLib | none (`types` default `[]` in both), default library of the target (`lib.es2025.full.d.ts`), not set, false | defaults (equal) |

The runner checks `files` against the parse set and `priority` against the requested class before timing (section 2); for the parse+bind configurations (`*-bind`, `*-bind-single`) it also checks the driver name and `symbols` > 0; for the check configurations (`*-check`, `*-check-single`) the driver name, a `diagnostics` count and `programFiles` > `files` (the default library is in the program). `bench.mjs --check` runs only this validation, once per selected configuration and repository plus the empty file list, and prints the counts (functional check, no timing, nothing written).

## 5. Measurement

- **[DECISION B6] hyperfine with `--shell=none`.** No shell between hyperfine and the driver, so there is no shell start-up in the numbers and no shell-dependent noise. Commands are passed with forward-slash paths because hyperfine splits them by POSIX shell-word rules, in which a backslash is an escape character.
- **Absolute executable paths only.** On the reference machine, `node` on PATH is a Volta shim that starts the real Node as a child process. Through the shim, peakmem reported 13 MB peak working set for a run that actually peaks at 115 MB: the shim's memory, not Node's. The harness never resolves executables through PATH.
- **[DECISION B7] Fixed order, no interleaving.** For each repository, the configurations run in the order of section 1; hyperfine runs all N runs of one configuration before the next. Interleaving would spread slow drift (thermal, background) evenly; it is not done because hyperfine does not support it and a custom runner is one more thing to defend. The variance gate (section 6) is the safeguard against drift.
- **[DECISION B8] Peak memory = peak working set** (`PeakWorkingSetSize`, the Windows counterpart of peak RSS), plus peak commit (`PeakPagefileUsage`), read after exit with `GetProcessMemoryInfo` on the still-open process handle by `peakmem` (.NET 10). Measured in separate runs so that timing is not affected; median of M runs (default 5).
- **[DECISION B9] Drivers run in the high priority class.** With `--priority high` (the default), `bench.mjs` sets `NEVERSHARP_PRIORITY=high`; every driver raises its own process to `HIGH_PRIORITY_CLASS` as its first action (Go: `SetPriorityClass` via `golang.org/x/sys/windows`; Node: `os.setPriority`) and reports the class in effect, and the runner rejects a driver whose report differs. Reason: on the reference machine the idle baseline is 7–10 % CPU, mostly kernel time, and short parallel runs (0.1–0.15 s on 24 threads) are as slow as their slowest thread, so any preempted core stretches the run (section 8). High priority lets the measured process preempt normal-priority background work, for every configuration alike; the C# driver must do the same. It needs no administrator rights and changes nothing on the system beyond the lifetime of the process. Why not simpler: Windows does not pass a high priority class on to child processes, so starting hyperfine at high priority would leave the drivers at normal priority; a job object with a priority-class limit would cover children, but needs a privilege that normal users do not have (`ERROR_PRIVILEGE_NOT_HELD`); a launcher process per run would add its own start-up to every measurement. hyperfine itself stays at normal priority. The effect on variance is not yet measured (section 8).
- **Statistics.** Median and MAD (median absolute deviation, unscaled) over the N timed runs. Throughput = parse-set file count and on-disk bytes / median wall-clock. MB = 10^6 bytes.
- **Defaults:** N = 20 timed runs after 3 warmup runs, M = 5 memory runs.

## 6. Rig checks and the variance gate

Before every run, `env.mjs` records the environment and checks the rig settings of [hardware.md](hardware.md):

| Check | Required |
|---|---|
| `min-processor-state` | minimum processor state (AC) = 100 % |
| `max-processor-state` | maximum processor state (AC) = 100 % |
| `boost-off` | `% Processor Performance` under a 2.5 s all-core load ≤ 101 % (no clock above nominal) |
| `idle-before-run` | median CPU utilization of ten consecutive 1 s windows before the run < 12 % (B10); all ten values are recorded. Read from the OS processor-time counters (`os.cpus()`), so the check starts no process of its own |
| `harness-committed` | clean working tree: every number comes from a committed harness |

A run with any failed check is written with `protocolCompliant: false`; the report marks it as a **probe** and it is never reported as a result. The Defender path exclusion cannot be verified without administrator rights and is recorded as such.

- **[DECISION B10, CONFIRMED 2026-10-21] Idle limit 12 %.** The limit was first set to 5 % before the machine's baseline was known. Measured repeatedly with nothing else running, the reference machine idles at 7–10 % CPU, mostly kernel time that no user process accounts for; at 5 % no run could ever be protocol-compliant. 12 % is the measured baseline plus a margin. The check still catches a second workload (in run C, other work on the machine pushed it to 40 %).
  - **Amended 2026-10-21 (confirmed by the author): median of ten 1 s windows instead of the mean of one 3 s window.** With the single 3 s window, runs F and G failed the check at their start (30.7 % and 20.3 %) although the machine measured 3–12 % in repeated 3 s windows between runs, and run G then passed the rig check with its best values so far. A single short window is decided by momentary spikes (the terminal, a remote display session) rather than by a second workload. The median of ten 1 s windows ignores a spike of a few seconds and still fails when another workload runs throughout. A first test of the new check: median 7.9 %, individual windows 2.8–18.2 %. The limit of 12 % is unchanged.
- **[DECISION B11, CONFIRMED 2026-10-21] Variance gate (kill criterion 3) = rig check on the single-threaded configurations; parallel configurations report their spread; verdicts use confidence intervals.**
  - The gate: in a protocol-compliant run, every **single-threaded** configuration (`tsc6-parse`, `tsgo7-parse-single`, later the single-threaded C# configurations) on every repository must have MAD/median < 3 %. If not, the rig is not fit to publish numbers.
  - **Amended (prereg/v4, 2026-10-22), decided after seeing two runs:** the gate binds `tsc6-parse`, `tsgo7-parse-single` and the primary single-threaded C# configuration of each track (`cs-aot-ws-single`, later `cs-o-aot-ws-single`). The other single-threaded C# configurations (JIT, Server GC) report their spread like the parallel ones; where a secondary result above 3 % is used, it carries a variance note. Reason: in M6 runs 1 and 2 (`results/m6/`) the rig configurations stayed at or below 1.43 % and `cs-aot-ws-single` at or below 1.68 %, while JIT and Server-GC "single-threaded" configurations reached 3.36–5.08 %; those runtimes run background compilation and per-core GC threads, so their spread is a property of the program, the same argument as for the parallel configurations below.
  - **Parallel** configurations (`tsgo7-parse`, later parallel C# configurations) are not gated. Their MAD/median is reported in every run, next to the median.
  - **Relative claims** (the parity hypothesis, any "X is N× faster") use the ratio of medians with a 95 % percentile-bootstrap confidence interval (10,000 resamples of both samples, fixed seed; geometric mean over repositories resamples all of them jointly). The exact decision rule for the parity claim on this interval is fixed in the pre-registration document.
  - Why: across five probe runs, single-threaded configurations stayed at 0.3–2.8 %, except two cells in run A (3.69 % and 3.85 %, uncommitted work and an IDE running), while parallel typescript-go on the three short repositories (0.10–0.16 s per run) spread 2–6 %. Neither the Defender exclusion, nor running the drivers at high priority (B9), nor GC counts explain the spread (section 8). The spread belongs to the parallel program: a 24-thread run of 0.1 s is sensitive to how work and GC fall onto threads in each run. A rig fix cannot remove it, and gating on it would make the three small repositories unusable as baselines, i.e. drop part of Microsoft's corpus in effect.
  - **Disclosure:** this decision was taken after seeing probe data, and it narrows the scope of a gate that this document had earlier said must not be relaxed. It was taken before any C# code or port number exists, and the probe data on which it rests are listed in section 8. The 3 % threshold itself is unchanged.

## 7. Result schema and report

- `artifacts/bench/results/<runId>/run.json`, schema [harness/bench/result.schema.json](../harness/bench/result.schema.json) (`schemaVersion` 1): environment, rig checks, corpus hashes, settings (including the drivers' priority class), configurations (including `threads`: single or parallel), and per (repository, configuration): command, driver output, all timed runs, median, MAD, MAD/median, throughput, memory runs, runtime metrics (C# only), raw hyperfine export.
- `report.mjs` produces the protocol's tables:
  1. wall-clock, throughput and peak memory per repository and configuration;
  2. median wall-clock relative to `tsgo7-parse`, per repository and geometric mean, each with its 95 % confidence interval;
  3. the variance gate: single-threaded rows binding (rig check), parallel rows reported;
  4. runtime metrics of C# configurations (bytes allocated, GC count per generation, total GC pause).

  The BenchmarkDotNet table (in-process, supplementary) is added with the first C# code.

Findings, in the order they were made:

1. **Defender is not the cause** (A → B). The high system time of parallel typescript-go, about 5× its wall-clock, was first attributed to on-access scanning. With the exclusion in place the ratio is unchanged (A: 4.7–6.1, B: 4.6–5.6); it belongs to the parallel run itself (24 threads, memory commit, scheduling).
2. **Background load matters for parallel runs** (C, D). With other work on the machine (C) or without (D), single-threaded rows pass; parallel rows improve once other work stops but still fail on the three shortest repositories (medians 0.10–0.16 s). The 40.7 % reading in C was checked against Windows' own counters and was real.
3. **The idle baseline is 7–10 %** (D and repeated checks), mostly kernel time. The 5 % limit was unattainable → B10.
4. **High priority does not remove the spread** (E). With every driver in the high priority class, parallel rows are at 1.99–4.35 %; playwright and bluesky still fail, tldraw passes, vscode gets worse. Sorted per-run times are evenly spread (playwright: 132–154 ms), not a tight cluster with outliers.
5. **GC count does not explain it** (diagnostic, not a protocol run). Playwright, parallel, high priority, 20 runs with `GODEBUG=gctrace=1`: 141–160 ms wall-clock, 8–10 GC cycles per run, 3.7–8.6 ms total stop-the-world pause; correlation between wall-clock and GC cycle count 0.19.
6. **Conclusion → B11.** The spread is a property of short parallel runs of the measured program, not of the rig.
7. **The idle check, not the machine, failed F and G** → amendment of B10. Both runs passed the rig check (G with its best values so far) but failed `idle-before-run` at their start. A test whether the version calls `bench.mjs` makes just before the check inflate the reading was negative; the load simply fluctuates between 3 % and 12 % in 3 s windows, with occasional spikes.

Post hoc observation, probe data, not a result: tsc 6.0.3 takes about 11–12× the wall-clock of parallel typescript-go for parsing (run E: geometric mean 11.94, 95 % CI [11.81, 12.11]; run G: 12.24 [12.08, 12.38]), and single-threaded typescript-go is 2.2–3.1× faster than tsc 6.0.3 (run A). ## 10. Driver cross-check (A6)

`node crosscheck.mjs <run.json>` compares, per repository, the Go driver's parse time (median of `tsgo7-parse` minus its fixed cost) with the parse time tsgo reports about itself (`Parse time` from `--extendedDiagnostics` on a generated tsconfig with exactly the parse set, `noResolve`, `noLib`; median of 5). tsgo's phase includes program-construction work the driver does not do, so the driver should not be slower; a ratio well above 1 would mean the driver handicaps Go.
