# Benchmark harness (Phase 0, task 2)

Status: draft, built 2026-10-14. Items marked **[DECISION]** are open to veto before the pre-registration tag.
Code: [harness/bench/](../harness/bench/).

## 1. What it measures

Phase 1 compares parsers, so the benchmark is **parse-only**: read every source file of a repository and parse it, the way a compiler's program loader does, and keep all syntax trees alive until the end. Full type-checking builds (`tsc -p` against `tsgo -p`, Microsoft's published comparison) are not part of Phase 1; see section 9.

Configurations (all reported; none is dropped after the fact):

| Id | What runs |
|---|---|
| `tsc6-parse` | tsc 6.0.3 compiler API on Node 24.21.0, single-threaded (as tsc is) |
| `tsgo7-parse` | typescript-go 7.0.2 parser, parallel: typescript-go's default |
| `tsgo7-parse-single` | typescript-go 7.0.2 parser, single-threaded: what tsgo's `--singleThreaded` switches |
| C# configurations | added in Phase 1: .NET 10 JIT and NativeAOT, each with Workstation and Server GC |

## 2. Pipeline

```
node scripts/fetch-references.mjs          # TypeScript, typescript-go, five benchmark repos at pinned commits
node scripts/install-tools.mjs             # Go (Microsoft build), Node, hyperfine into .tools/, SHA-256 verified
cd harness/bench && npm ci                 # typescript@6.0.3 and typescript@7.0.2 (npm aliases), lockfile-pinned
node filelists.mjs                         # parse sets per repo + manifest (counts, bytes, content hash)
node build-go.mjs                          # Go parse driver, built like Microsoft's tsgo release binary
dotnet build peakmem -c Release -o ../../artifacts/bin/peakmem
node bench.mjs [--repos …] [--configs …] [--runs 20] [--warmup 3] [--mem-runs 5] [--label …]
node report.mjs artifacts/bench/results/<runId>/run.json
```

`bench.mjs` must be started with the pinned Node (`.tools/node-24.21.0/node.exe`), so the harness itself does not run behind the Volta shim.

For each (repository, configuration) pair, `bench.mjs` does three things, in this order:

1. **Validation run.** The driver prints a JSON line with the number of files it parsed; it must equal the file count of the parse set.
2. **Wall-clock** with hyperfine: `--shell=none`, warmup runs, then N timed runs, JSON export.
3. **Memory pass**, separate from timing: the driver runs under `peakmem` M times; the median peak working set and peak commit are reported.

## 3. Parse set

**[DECISION B1] The parse set of a repository is every git-tracked file with extension `.ts .tsx .mts .cts` (including `.d.ts`) at the pinned commit.** No file is added or removed by hand. It is generated by `filelists.mjs`, which also records the file count, total bytes and a SHA-256 over all paths and contents; every run.json carries these values.

| Repository | Files | MiB |
|---|---:|---:|
| vscode | 11,724 | 134.6 |
| sentry | 8,932 | 43.8 |
| bluesky | 1,688 | 6.9 |
| playwright | 1,415 | 16.4 |
| tldraw | 2,508 | 13.0 |

This is a superset of what `tsc -p` compiles in these repositories: it includes tests, fixtures and tooling. For example, VS Code's set contains an 8.1 MiB copy of TypeScript's `checker.ts` used as a colorizer fixture. The alternative, the file list of each project's tsconfig (`--listFilesOnly`), requires installing every repository's dependencies and choosing a tsconfig per repository; both are choices a reviewer could attack. The git rule has no free parameter. The same set is part of the equivalence corpus ([ast-dump-format.md](ast-dump-format.md)), so every file that is timed is also checked for equivalence.

## 4. Parse-only drivers

Both drivers read a file list, read and parse each file, keep every syntax tree referenced until the end, and print one JSON line (files, characters/bytes, node count).

| | tsc 6.0.3 (`parse-ts.mjs`) | typescript-go 7.0.2 (`go/parse.go`) |
|---|---|---|
| Read | `ts.sys.readFile` | `osvfs.FS().ReadFile` |
| Parse | `ts.createSourceFile(file, text, { languageVersion: Latest, jsDocParsingMode: ParseForTypeErrors }, setParentNodes=false, scriptKind)` | `parser.ParseSourceFile(opts, text, core.GetScriptKindFromFileName(file))` |
| JSDoc | `ParseForTypeErrors`: what `executeCommandLine.ts` sets for tsc (JSDoc in JS files; in TS files only comments with `@see`/`@link`) | lazy in TS files except `@see`/`@link`: the same effective scope |
| Scheduling | sequential | `core.NewWorkGroup(single)`: typescript-go's own work group, one work item per file (read + parse), as `compilerHost.GetSourceFile` in `internal/compiler/host.go` does |
| Build | npm `typescript@6.0.3`, integrity-checked | Microsoft Go 1.26.4-1, `-trimpath -ldflags="-s -w" -tags=noembed`, `CGO_ENABLED=0`, `GOAMD64=v1`: identical to the release binary's `go version -m` except `vcs.modified` |

Decisions:

- **[DECISION B2] Trees stay alive until the end.** A program holds every source file. Discarding each tree after parsing made peak memory and GC work unrealistically small; in a first smoke test, single-threaded Go peaked at 18 MiB instead of 143 MiB on bluesky. A C# port would profit from the same artifact.
- **[DECISION B3] The tsc driver uses `ParseForTypeErrors`**, the mode tsc itself uses, and typescript-go's effective scope. The equivalence dump uses `ParseAll`, because there more coverage is better. The C# port is measured in the same mode as tsc.
- **[DECISION B4] typescript-go is measured parallel and single-threaded; the parallel default is the baseline** in relative comparisons, because that is typescript-go's wall-clock. Parallel parsing has a counterpart in typescript-go (`core.WorkGroup` in `internal/compiler/program.go`), so under the port rules the C# port may parallelize parsing the same way.
- **[DECISION B5] The Go driver is ours, the parser and scheduling are Microsoft's.** There is no parse-only mode in the tsgo CLI. The driver is a loop of about 30 lines around `core.WorkGroup`, `osvfs` and `parser.ParseSourceFile`, compiled with Microsoft's toolset and flags. This is the one place where the Go side contains code we wrote; it is kept minimal and is published.

## 5. Measurement

- **[DECISION B6] hyperfine with `--shell=none`.** No shell between hyperfine and the driver, so there is no shell start-up in the numbers and no shell-dependent noise. Commands are passed with forward-slash paths because hyperfine splits them by POSIX shell-word rules, in which a backslash is an escape character.
- **Absolute executable paths only.** On the reference machine, `node` on PATH is a Volta shim that starts the real Node as a child process. Through the shim, peakmem reported 13 MB peak working set for a run that actually peaks at 115 MB: the shim's memory, not Node's. The harness never resolves executables through PATH.
- **[DECISION B7] Fixed order, no interleaving.** For each repository, the configurations run in the order of section 1; hyperfine runs all N runs of one configuration before the next. Interleaving would spread slow drift (thermal, background) evenly; it is not done because hyperfine does not support it and a custom runner is one more thing to defend. The variance gate (section 6) is the safeguard against drift.
- **[DECISION B8] Peak memory = peak working set** (`PeakWorkingSetSize`, the Windows counterpart of peak RSS), plus peak commit (`PeakPagefileUsage`), read after exit with `GetProcessMemoryInfo` on the still-open process handle by `peakmem` (.NET 10). Measured in separate runs so that timing is not affected; median of M runs (default 5).
- **Statistics.** Median and MAD (median absolute deviation, unscaled) over the N timed runs. Throughput = parse-set file count and on-disk bytes / median wall-clock. MB = 10^6 bytes.
- **Defaults:** N = 20 timed runs after 3 warmup runs, M = 5 memory runs.

## 6. Rig checks and the variance gate

Before every run, `env.mjs` records the environment and checks the rig settings of [hardware.md](hardware.md):

| Check | Required |
|---|---|
| `min-processor-state` | minimum processor state (AC) = 100 % |
| `max-processor-state` | maximum processor state (AC) = 100 % |
| `boost-off` | `% Processor Performance` under a 2.5 s all-core load ≤ 101 % (no clock above nominal) |
| `idle-before-run` | mean CPU utilization over 1.5 s before the run < 5 % |
| `harness-committed` | clean working tree: every number comes from a committed harness |

A run with any failed check is written with `protocolCompliant: false`; the report marks it as a **probe** and it is never reported as a result. The Defender path exclusion cannot be verified without administrator rights and is recorded as such.

**Variance gate** (kill criterion 3): every baseline configuration on every repository must have MAD/median < 3 % in a protocol-compliant run before any port numbers are published.

## 7. Result schema and report

- `artifacts/bench/results/<runId>/run.json`, schema [harness/bench/result.schema.json](../harness/bench/result.schema.json) (`schemaVersion` 1): environment, rig checks, corpus hashes, settings, and per (repository, configuration): command, driver output, all timed runs, median, MAD, MAD/median, throughput, memory runs, runtime metrics (C# only), raw hyperfine export.
- `report.mjs` produces the protocol's tables:
  1. wall-clock, throughput and peak memory per repository and configuration;
  2. median wall-clock relative to `tsgo7-parse`, per repository and geometric mean;
  3. the variance gate;
  4. runtime metrics of C# configurations (bytes allocated, GC count per generation, total GC pause).

  The BenchmarkDotNet table (in-process, supplementary) is added with the first C# code.

## 8. Probe results

Two full runs with protocol settings (N = 20 after 3 warmup runs, M = 5, all repositories and configurations). **Both are probes, not protocol results:** in both, `harness-committed` failed (uncommitted harness changes) and `idle-before-run` failed (an IDE and the assistant session were running). Nothing below is a published number; it is input for fixing the rig.

| Run | Defender exclusion | Idle CPU before run |
|---|---|---|
| A `2026-10-14T17-05-33-178Z` | no | 9.7 % |
| B `2026-10-14T17-27-54-080Z` | yes (applied by the maintainer between A and B) | 18.0 % |

MAD/median per configuration and repository (gate: < 3 %), run A / run B:

| Configuration | vscode | sentry | bluesky | playwright | tldraw |
|---|---:|---:|---:|---:|---:|
| tsc6-parse | 1.41 / 0.89 | **3.69** / 1.32 | 0.91 / 1.83 | 0.48 / 1.24 | 2.08 / 1.36 |
| tsgo7-parse | **3.25** / **3.13** | 1.91 / **4.40** | **3.15** / **6.02** | **3.30** / **3.26** | **3.36** / **3.17** |
| tsgo7-parse-single | **3.85** / 0.66 | 0.30 / 1.56 | 1.59 / 1.15 | 0.64 / 1.08 | 0.92 / 0.86 |

Variance gate: fail in both runs. In run B, all tsc and single-threaded Go cells pass (0.66–1.83 %); all five parallel Go cells fail (3.13–6.02 %).

Findings:

- **The Defender hypothesis was wrong.** After run A, the high system time of parallel typescript-go (about 5× its wall-clock) was attributed to on-access scanning. With the exclusion in place, the ratio is unchanged (A: 4.7–6.1, B: 4.6–5.6). The system time belongs to the parallel run itself (24 threads, memory commit, scheduling), not to the scanner. The exclusion stays in place as specified in hardware.md, but it does not explain the variance.
- **Working hypothesis:** a parallel run of 0.1–0.5 s that occupies all 24 hardware threads is as slow as its slowest thread, so any background activity that takes a core for a moment stretches the whole run; a single-threaded configuration is simply scheduled on another free core. That matches parallel-only failures with 10–18 % background load. It is untested until a run on an idle machine exists.

Next steps, before any port number exists:

1. A run from a committed harness on an idle machine (IDE, browser and assistant closed), started by the maintainer.
2. If the parallel configuration still fails on an idle machine: investigate and fix the rig. Not acceptable as fixes: changing the threshold, dropping the configuration, changing GOMAXPROCS (it would no longer be typescript-go's default), or raising N (that sharpens the MAD estimate, it does not reduce the spread). Any change to the measurement method is an amendment before the pre-registration tag.

Note: the variance gate blocks *publishing* port numbers (kill criterion 3), not porting. Phase 1 work can start while the rig is being fixed.

Post hoc observation, probe data, not a result: tsc 6.0.3 takes 9.9–11.9× the wall-clock of parallel typescript-go for parsing (run A, geometric mean 11.2×), and single-threaded typescript-go is 2.2–3.1× faster than tsc 6.0.3. The order of magnitude matches Microsoft's published ~10× for full builds.

## 9. Not covered yet

- **Full builds** (`tsc -p` / `tsgo -p` per repository, Microsoft's published comparison). Reproducing them would show that the rig reproduces Microsoft's ratio, but it requires installing each repository's npm dependencies (thousands of packages, several GB) and picking a tsconfig per repository. Proposed as a separate, optional step (with `--ignore-scripts`), labeled as a rig sanity check, not as a protocol metric for Phase 1.
- **C# configurations** and BenchmarkDotNet: with the first ported code.
- **Linux or macOS**: `env.mjs` and `peakmem` are Windows-only, matching the reference machine.
